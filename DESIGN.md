# Design: ai-app-factory

## Problem

Every recent project (`nautobot-app-pytest-compliance-rule-engine`, `uk-wealth-tracker`, `cloud-netbox-eval`, `cloud-nautobot-eval`, `PLC`, ...) has re-derived the same unattended Claude Code build pipeline from scratch in conversation: create a repo, set `CLAUDE_CODE_OAUTH_TOKEN`/`GH_PAT` secrets, write a `.env`, add a `claude-go`/`model:opus`/`lane:*` label taxonomy, a `.github/workflows/claude.yml` that runs `claude-code-action` per labeled issue, a `docs/journal.md` metrics log, and milestones. The pattern is proven; only the re-deriving is wasted effort.

## Goal

`ai-app-factory` is two things:

1. **Templates + CLI** — package the repo-scaffolding boilerplate above as reusable templates (`nautobot-app`, `netbox-plugin`, `custom-script`) plus a small CLI that creates a new repo, sets its secrets from a local store, and wires labels/milestones in one step.
2. **The factory site** — a static SvelteKit dashboard (GitHub Pages) that (a) turns a vague ask into a drafted design doc for approval, (b) turns an approved design doc into GitHub milestones/labeled issues, and (c) shows every tracked project in one place: grouped sidebar, original ask, start date, elapsed time, token-burn history, latest Actions run status, commit heatmap.

## Non-goals

- Scraping the claude.ai usage page. It's an authenticated interactive UI with no public API; automating a login to get at it is fragile and out of scope. Token burn instead comes from `docs/journal.md` (which `claude-code-action` already populates with real per-issue duration/turns/tokens/cost), and "session status" comes from the GitHub Actions run state.
- A custom rich-text editor for design docs. Drafting produces a PR; approval/editing happens in GitHub's own PR review UI.
- A separate hosting account. Everything — frontend and the write-side actions that need secrets — runs on GitHub (Pages + Actions).

## Architecture

**Read path (dashboard):** 100% static. The SvelteKit site, deployed to GitHub Pages, reads `projects.json` (this repo, the project registry) plus each tracked repo's public GitHub REST/GraphQL API (issues, milestones, Actions runs, `stats/commit_activity`) and raw `docs/journal.md` — all directly from the browser, no server needed.

**Found live, 2026-08-18, present since M3: every project detail page 404'd** — nobody had clicked one on the actual deployed site until then, only ever verified this route's data via API/`gh` checks. The route was `/projects/[repo]` with `repo` built as `encodeURIComponent('owner/name')`, so `adapter-static` happily prerendered a file literally named `projects/mmorrow24work%2Fai-app-factory-hello-world.html` — but GitHub Pages, like most static hosts, decodes `%2F` in the *incoming request path* before matching it to a file, so the live URL never resolves to that file regardless of how correctly it was built. Confirmed by serving the actual build locally with `serve` (which replicates GitHub Pages' extensionless-URL resolution, unlike Python's `http.server`) and seeing the same 404 offline. Fixed by switching to two real path segments, `/projects/[owner]/[name]` — no encoding involved anywhere, so no host's slash-decoding can break it — verified by re-serving the build and confirming 200 with correct content, matching an already-known-working route.

**Write path (drafting, generating issues):** the `/new` page builds a pre-filled GitHub "New issue" link (`issues/new?title=[new-project-ask] ...&body=...`) rather than calling any authenticated API — the requester fills out project name + requirements on the site, is redirected to GitHub, and clicks GitHub's own submit button there. `draft-design-doc.yml` triggers on `issues: opened`, filtered to a `[new-project-ask] ` title prefix, and reads the issue's title/body directly — no credential of any kind ever touches the requester's browser, and the issue's author (`github.event.issue.user.login`) is the requester's identity, authenticated by GitHub itself rather than self-reported. A workflow drafts the design doc via Opus and opens it as a PR; on merge, a second workflow reads the approved doc and opens a **provisioning issue in `ai-app-factory` itself** — it does not create the target repo or touch any other repo. A human runs `scripts/factory-new.sh` + `scripts/factory-secrets.sh` locally (their own `gh auth`, no stored credential involved) to actually create it, then manually fires that new repo's own `seed-milestones.yml` (`workflow_dispatch`, no inputs) to turn the design doc into milestones and `claude-go`-labeled issues, using *that repo's own* narrowly-scoped secrets rather than reaching back across from `ai-app-factory`. The full loop, step by step, is documented in `docs/adr/0001-design-to-issues-loop.md`.

**Found via a real end-to-end test (2026-08-18): a `labels=` query param on an `issues/new` deep link is silently dropped for anyone who isn't already a repo collaborator with label-write access.** The original design used `labels=new-project-ask` to trigger `draft-design-doc.yml`; a live test (opening a real issue exactly as the site would) passed, but only because it was opened by the repo owner, who has that permission and so structurally couldn't have caught the failure mode that matters — an actual arbitrary requester's label would vanish, the issue would open unlabeled, and nothing would fire, silently. `title` and `body` query params carry no such restriction; they're honoured for any GitHub user. Fixed by moving the trigger condition onto a `[new-project-ask] ` title prefix instead — the workflow still applies the label itself server-side afterward, but purely for bookkeeping, never for triggering. A second, not-yet-built mechanism has the identical bug baked into its design and needs the same fix before implementation — see the `review-approve`/`review-reject` note under "PR review & merge" below.

This puts two human approval gates between "someone had an idea" and "tokens start getting spent on it": merging the design-doc PR, then separately choosing to provision the repo. The second gate is deliberate, not just a security boundary — it's the point where you see who's asking for what and can decide whether it's worth building before any Opus run against the new repo (milestone/issue generation, then every `claude-go` issue after it) starts burning tokens.

**Why the write-path credential can't be hardcoded into the site instead of user-supplied.** `ai-app-factory`'s frontend is 100% static (GitHub Pages) — every file it serves, including its compiled JS bundles, is public and unauthenticated by construction; there is no server between a visitor and those files. Anything baked into a shipped `.js` file is therefore readable by anyone who requests it (`curl` the bundle, or open devtools → Sources) — no amount of minifying/encoding survives this, and GitHub's own secret scanning actively detects and auto-revokes recognizable tokens pushed to public repos regardless. A leaked write-path credential could trigger `draft-design-doc.yml` — i.e. spend real Claude Code turns/tokens — an unlimited number of times, from anywhere, indefinitely, with no way to distinguish a real request from abuse until the bill or the spam shows up. This is the same failure mode `GH_PAT: token strategy` below exists to prevent for the provisioning step; hardcoding a site-wide credential would reintroduce it at the front door instead, at internet-wide scale rather than merely at risk of it. Settled 2026-08-18, in conversation rather than by incident — recorded so it doesn't get re-proposed.

**Resolved 2026-08-18: the original localStorage-PAT design assumed whoever submits `/new` already has a fine-grained GitHub PAT** — true for this repo's operator, not for an arbitrary requester the "request a new app" flow is meant to serve. Settled on the issue-deep-link mechanism described in the Write path paragraph above; the remaining tradeoff is that the requester still needs *a* GitHub account (unavoidable without standing up real backend infra), and it's a two-hop flow (site form → GitHub page → their submit click) instead of one click.

**Found via a real non-collaborator test account (2026-08-18): `claude-code-action` itself refuses to run for any actor without write access to the repo, by default** — a check baked into the third-party action, separate from and downstream of the trigger-mechanism fix above. Every real requester fails this by construction, since the whole point of this workflow is serving people who aren't collaborators; every test up to this point had passed only because it was run by the repo owner or a collaborator, so nothing surfaced this until an actual outside account (`mmorrow2012`) tried it for real and got `Actor does not have write permissions to the repository`. Fixed with the action's own `allowed_non_write_users: "*"` input, accepted despite its own documented prompt-injection warning because the blast radius is already bounded independent of it: `GH_PAT` is scoped to this one repo, excludes `Administration`/`Workflows`, and `draft-design-doc.yml`'s `--allowedTools` grants no network/curl access — there's no path out of this repo even for a successful injection, and gate #1 (reviewing/merging the drafted PR) is still the real control point regardless of who or what drafted it.

**Found the same day, one step later in the loop: `claude-code-action` also refuses to run for a `workflow_dispatch` initiated by a bot actor, by default.** `generate-issues.yml`'s own `dispatch` job self-fires the `generate` job's `workflow_dispatch` via `gh workflow run`, authenticated as `GITHUB_TOKEN` — deliberately, so the resulting issue is opened by `github-actions[bot]` rather than the account owner (see the `github_token` comment in that workflow: `GH_PAT` authenticating as the owner meant GitHub never notified them about their own account's actions). That same bot identity is exactly what `claude-code-action` blocks by default: `Workflow initiated by non-human actor: github-actions (type: Bot)`. First real merges of #42/#43 hit this — two provisioning issues that should have been opened, weren't. Fixed with `allowed_bots: "github-actions[bot]"`, scoped to that one bot rather than `'*'`, since this workflow only ever self-dispatches from a real push after a real human merge — there's no arbitrary-bot surface here worth widening for.

**A fourth bug the same day, and a genuinely funny one: the requester-stamp dedup check false-positived on a design doc that was *about* the stamp itself.** `ai-app-factory-hello-world-v3`'s doc (from intake issue #41, a deliberate test of requester-driven authorization) extensively discusses its own `**Requested by:**` mechanism in prose while explaining what it's testing — and `draft-design-doc.yml`'s dedup check, `grep -qF "**Requested by:**" "$doc"` searching the *whole file*, found that prose quote and concluded the doc was already stamped, skipping the actual insertion at the top. The PR body got stamped correctly (different, narrower bug hadn't hit that check yet), so nothing looked obviously wrong until `generate-issues.yml`'s own drafted provisioning issue (#45) noticed the doc on `main` was missing the line and flagged it as worth checking. It was real. Fixed by checking only where the stamp actually lands — line 3 of the doc, line 1 of the PR body — instead of the whole text, verified by reproducing the false-positive locally against the old check and confirming the new one doesn't trip on it. The already-broken doc was backfilled directly on `main` rather than left wrong.

**Requester PII is deliberately minimized to their GitHub account name — nothing else is collected.** An earlier version of this design collected name/email/phone as free-text form fields (see the M5 milestone note); superseded the same day it shipped, for two reasons. First, a free-text field is self-reported and unverifiable — anyone could type any name — while the issue-deep-link mechanism gives an *authenticated* identity for free (the issue author, confirmed by GitHub's own login, unspoofable) without asking the requester for anything extra. Second, minimizing PII matters on a fully public, unauthenticated static site (see "Visibility" under "Multiple concurrent projects" below) — a GitHub handle is already-public information the requester chose to make public themselves by having an account, whereas a phone number or personal email is real PII this system would otherwise be republishing on their behalf. Operationally: the owner's moderation model is simply recognizing (or not) the GitHub account behind an ask — an unrecognized account's project request gets ignored rather than approved at gate #1, which is the entire reason the identity needs to be authenticated rather than self-reported.

**Found live, 2026-08-18: a long, real requirements submission broke GitHub's own URL length limit.** Every test up to that point used a one-line ask; a real multi-section spec (several KB) hit GitHub's "Whoa there! Your request URL is too long" error on submit, because `body=` on the pre-filled `issues/new` link scaled directly with whatever the requester typed, with no cap. Fixed by taking requirements text out of the URL entirely — the link now carries only the (short) title and a constant placeholder body; the real text goes to the visitor's clipboard via `navigator.clipboard.writeText()` for them to paste over the placeholder on GitHub's own page, which has no such limit. `/new` now opens GitHub in a new tab rather than navigating away, so it can show a status message (including a fallback if the clipboard write itself fails) rather than silently trusting the copy worked. Verified the generated URL stays a fixed ~285 characters regardless of requirements length.

**Repo-scaffolding boilerplate:** codified once in `templates/_shared/labels.json` and per-type templates under `templates/`, applied by `scripts/factory-new.sh` / `scripts/factory-secrets.sh`, which read known values (`CLAUDE_CODE_OAUTH_TOKEN`, `GH_PAT`, default cloud NetBox/Nautobot URLs and API keys) from `~/.config/ai-app-factory/.env` so they're set once, not re-typed per project.

**Found live, 2026-08-18: `factory-new.sh`'s `{{KEY}}` substitution silently corrupted any rendered value containing `&`.** Bash 5.1+'s `${var//pattern/replacement}` treats an unescaped `&` in the *replacement* text as "the matched pattern" (`sed`-style), not a literal ampersand — undocumented in this script, and dormant until a real value (`SUPPORT_HANDOFF.md.tmpl`'s new "Support & feedback" heading, added the same day) first contained one. The output spliced the literal, unrendered `{{key}}` token back into the middle of its own replacement text — reproduced in isolation (`X="AAA & BBB"` → `"AAA {{X}} BBB"`) before touching the real script. Fixed by escaping `\` then `&` in every value before substitution, verified against the same repro and a real `factory-new.sh --dry-run` render.

**Found live, 2026-08-19: `factory-new.sh` provisioning the factory's first real (non-test) project, `ai-app-factory-cov-pubs`, aborted mid-run — repo created, labels partially applied, `projects.json` never touched.** `model:haiku`'s description in `labels.json` was 117 characters; GitHub's label API rejects anything over 100 with a 422, and since that check runs inside the label-application loop under `set -euo pipefail`, the whole script died there — after `gh repo create` had already run, but before every later label and the `projects.json` registration step. Fixed the description (down to 83 characters); finished this project's provisioning by hand (applied the corrected full label set to the already-created repo, added its `projects.json` entry matching the schema `factory-new.sh` itself writes) rather than delete and recreate the repo. Worth a defensive length check in `factory-new.sh` itself if this class of template-data typo recurs — not added here, since the actual fix (a `labels.json` typo) is what mattered this time.

**Web UI design system:** `templates/_shared/design-system/` (issue #30) is the standard for any future generated project that has a SvelteKit frontend of its own — the same Appearance/Colour palette/Typography system this site's own dashboard uses (issue #29), packaged with `{{PROJECT_NAME}}`-templated `localStorage` keys, ready to copy in by hand. Not auto-applied by `factory-new.sh`: none of the three current template types (`nautobot-app`, `netbox-plugin`, `custom-script`) include a SvelteKit frontend to apply it to — `nautobot-app`/`netbox-plugin` render through Nautobot's/NetBox's own UI, and `custom-script` projects (e.g. every `hello-world-v*` dogfood repo) are typically hand-written static HTML/CSS with no build step at all. Point here first before reinventing this for a future web-app template type.

**Static-site dark mode:** `templates/custom-script/theme.css` + `theme-toggle.js` (implemented 2026-08-18) — the framework-free counterpart, for exactly the static-site case the design system above doesn't cover. No build step, no npm packages: CSS custom properties toggled via a `data-theme` attribute on `<html>`, applied before first paint by a plain blocking `<script>` tag, with the toggle button auto-injected if a page doesn't already have one. Copied automatically into every new `custom-script` project by `factory-new.sh` (unlike the SvelteKit design system, no opt-in step) — `CLAUDE.md.tmpl` instructs the unattended pipeline to link both files into any HTML page it creates rather than inventing its own theming. Verified via a real `factory-new.sh --dry-run`: both files scaffold byte-identical (no placeholders to substitute), and `CLAUDE.md`'s rendered output correctly carries the linking instructions. Scoped to dark mode only, not the SvelteKit version's font-family/text-size pickers — a reasonable follow-up if wanted, not built in this pass.

**Journal convention:** the *workflow* appends metrics to `docs/journal.md` after each run (`.github/scripts/journal-entry.sh`, `if: always()`), never Claude's own branch. Adopted deliberately: `nautobot-app-pytest-compliance-rule-engine`'s journal documents that having Claude append its own entry inside each PR (as `uk-wealth-tracker` does) makes every open PR touch the same file, so almost every PR goes conflicting the moment any other PR merges.

## GH_PAT: token strategy

Earlier design had `generate-issues.yml` call `scripts/factory-new.sh` itself, which meant `GH_PAT` had to create repositories under `mmorrow24work` — and a fine-grained PAT scoped to "Only select repositories" **cannot** cover a repo that doesn't exist yet, so repo creation forced "All repositories" coverage (plus `Administration`) regardless of token type. That requirement is gone now: `ai-app-factory`'s own automation never creates or touches another repo at all (see the Write path paragraph above — provisioning is a human step, and milestone/issue seeding runs *inside* the new repo using *its own* secrets). `GH_PAT` on `ai-app-factory` only ever needs to operate on `ai-app-factory` itself.

**Decision: fine-grained PAT, scoped to "Only select repositories: `ai-app-factory`"**, with `Contents`, `Issues`, `Pull requests`, `Actions`, `Secrets` (Read and write) — not `Administration` (no repo creation needed here anymore), not `Workflows` (keeps `.github/workflows/*` changes behind human review, same reasoning as before). This is strictly narrower than either option the earlier "forced to All repositories" analysis compared — single-repo coverage *and* granular capability — because removing the repo-creation requirement removed the actual constraint that forced broad coverage in the first place.

**`GH_PAT` for generated projects is never stored anywhere — corrected twice on 2026-08-17 before landing here.** First attempt: a `.env`-stored value scoped to `Secrets: Read and write` only, reasoning that `factory-secrets.sh` itself just calls `gh secret set`. Wrong — that call authenticates with the *local* `gh` session, not this value; this value is the payload written into the new repo's own `GH_PAT` secret, which *that* repo's `claude.yml`/`seed-milestones.yml` then use for real Contents/Issues/Pull requests/Actions work. Found the hard way when `seed-milestones.yml` could create issues but 403'd on every milestone/label/comment/edit call during the M7 smoke test. Second attempt: broaden the same `.env` value to the full capability set, scoped to "All repositories" (unavoidable, since it's minted before the target repo exists). That fixed the immediate failure but reintroduced exactly the problem the `ai-app-factory`-own-token narrowing existed to solve, just relocated: one shared value copied into every generated project's secret means a leak from *any one* of them exposes a token that can act on *all* of them.

**Decision: `factory-secrets.sh` prompts for `GH_PAT` interactively (input hidden) on every run, and never persists it.** Mint a fresh fine-grained PAT scoped to "Only select repositories: `<that one repo>`" — which now works, since the repo already exists by the time `factory-secrets.sh` runs — with `Contents`, `Issues`, `Pull requests`, `Actions`, `Secrets` (Read and write), not `Administration`, not `Workflows`. More manual friction per project (a token to mint each time, not a one-time `.env` fill-in), but a leak from one generated project's secret can now never reach another's — true single-repo blast radius, not just single-repo *by convention*.

## PR review & merge: getting the human out of the loop, carefully

**As of 2026-08-18, reviewing and merging the PRs `claude.yml` opens is a manual step** — done today by a human (or a human-launched local Claude Code session) reading the diff, running the tests for real, and merging by hand. That means the pipeline is only as available as whoever's at their PC, which defeats a fair amount of the point of "unattended."

**Recommendation: a second GitHub Actions workflow, not an external server.** `claude.yml` already proves a GitHub Actions workflow can run Claude unattended end to end — the same pattern extends to review: a workflow triggered on `pull_request: opened` (scoped to PRs the pipeline itself opened) runs Claude in reviewer mode — check the diff, run the project's own tests for real, verify scope — and merges automatically if it passes. This fires the instant a PR appears, needs no PC, no new hosting, and stays on the same subscription-based `CLAUDE_CODE_OAUTH_TOKEN` billing the rest of this system already uses. An external server (Cloudflare Worker or otherwise) would only earn its keep for something GitHub Actions genuinely can't do — long-running state, sub-second reaction to a non-GitHub event — neither of which applies here; it would be infrastructure to secure and pay for with no upside over an in-repo workflow. Not yet implemented.

**First pass at a decision (2026-08-18, superseded below the same day): auto-merge on green within a defined safe scope, falling back to a human otherwise.** The initial concern was two real failure modes: *Claude reviewing Claude's own work has correlated blind spots* (a same-model self-check is good at "tests fail," weak at "technically passes but isn't what was asked for"), and *"reports success but did nothing" is an already-observed failure class in this exact system* (`track_progress` silently breaking PR creation, a missing checkout step, wrong token scope — all only caught because a human was watching closely). That reasoning led to a proposed split: product-ambiguity questions go to the requester, safety-flagged questions (touches `.github/`, new dependency, secrets touched, oversized diff) stay blocked for a human, because letting an interested party rubber-stamp their own flagged PR defeats the point of flagging it.

**Superseded: the owner does not want to be that human either, and the risk profile doesn't require one.** These are throwaway POC apps — the owner is explicitly fine with the odd project failing outright ("there will be a learning experience no matter what the result"), and the per-project `GH_PAT` (see `GH_PAT: token strategy`) already excludes `Administration` and `Workflows` scope, so even a requester rubber-stamping their own flagged PR structurally cannot touch `.github/workflows/*` or take any account-level action — the worst realistic outcome is a broken or compromised *single* throwaway repo, not blast radius beyond it. Given that, the product-ambiguity/safety-flagged split isn't buying enough to be worth the complexity, or the human dependency it would still require for the safety half.

**Decision: the requester gets full autonomy over their own project's review/merge decisions — every circuit-breaker case, no split.** The owner's involvement is fixed to exactly three touchpoints, unrelated to any individual PR: (1) approving the project's existence at all, by merging the design-doc PR — gate #1; (2) minting the project's scoped `GH_PAT` during provisioning — gate #2, and deliberately *not* delegable, since it's the actual credential rather than a decision about one; (3) archiving or deleting the repo once it's no longer needed (see "how it works" step 6). Every review/merge decision in between belongs to the requester, surfaced on the `ai-app-factory` site with a plain-language summary of what's pending and why. "Approve"/"Reject" are pre-filled GitHub "New issue" deep links — same zero-credential mechanism used for intake (see the Write path paragraph above) — titled `[review-approve] PR #<n>`/`[review-reject] PR #<n>`, filtered on that title prefix rather than a label for the same reason intake is: the requester is not a collaborator on the generated project's repo either (see "Support & handoff" below), so a `labels=` query param would silently fail exactly for them. A workflow triggered on `issues: opened` merges or closes the referenced PR using the *project's own* already-provisioned secret. No credential of any kind touches the requester's browser, and the owner is never in the decision path. The owner still gets a GitHub notification on every merge — passive visibility, not a required action, consistent with "not silent full autonomy" even though nothing here asks the owner to do anything.

**Implemented 2026-08-18: `templates/*/.github/workflows/review-decision.yml`**, identical across all three project types (no template placeholders needed — it's fully generic, driven by `github.repository` and the repo's own `README.md`). Also adds an authorization check the original decision didn't spell out: since this is a public repo with a public issue tracker, and the requester isn't a collaborator, *anyone* could otherwise open a `[review-approve] PR #<n>` issue and merge someone else's PR. The workflow parses the recorded requester's GitHub login back out of the repo's own README "Requested by" line (the same value `factory-new.sh` stamped in at provisioning) and only actions the decision if the issue's author matches that login or the repo owner — anyone else's issue is acknowledged and closed, not acted on. **Implemented 2026-08-18: the site UI too.** `site/src/lib/PendingDecisions.svelte`, rendered on each project's detail page — lists that repo's open PRs (a new `listOpenPullRequests` helper in `github.js`) with Approve/Reject links per PR, building the same `[review-approve] PR #<n>`/`[review-reject] PR #<n>` deep link `review-decision.yml` parses. Same zero-credential mechanism as `/new` throughout. Verified the generated URL decodes to exactly the expected title string before trusting it. This was scoped narrowly to the same day's earlier gap ("only reachable by hand-constructing the issue URL") rather than left as a follow-up, once it became clear that gap was blocking the actual point of the requester-autonomy exercise — testing v3/v4's PRs — not just a cosmetic nice-to-have.

**Verified live against `ai-app-factory-hello-world` (2026-08-18), both paths, and it caught a real bug on the first run.** The requester-extraction grep, run under `set -euo pipefail`, exits non-zero when it finds no match — the *expected* shape for any repo predating the "Requested by" section (hello-world does), meant to fall through to owner-only authorization. Instead `pipefail` propagated that as the whole pipeline's exit status, which `set -e` treated as the assignment statement failing, killing the step before the authorization `if` ever ran — silently blocking every decision on any older-format repo, including the one just tested. Fixed by appending `|| true` to the extraction pipeline. Re-verified after the fix: a real trivial PR approved via a real `[review-approve] PR #<n>` issue actually merged (squash + branch delete) and the intake issue was commented and closed; a second real PR rejected via `[review-reject] PR #<n>` actually closed without merging and its branch was deleted. Not yet verified: authorization actually *denying* a non-requester, non-owner login — doing so live would need a second GitHub account, so this path is confirmed by code review and local shell testing only, not a live run.

Separately, the upstream piece that *decides* when a PR needs a decision at all — the `pull_request: opened` reviewer workflow described above — is still not built. Without it, nothing currently opens a `[review-approve]`/`[review-reject]` issue automatically; this workflow only proves the execution half works.

**Found live, 2026-08-18: requester autonomy only ever covered approve/reject, never actually directing what gets built.** `review-decision.yml` lets the requester accept or decline a PR that already exists; `@claude` comments — `claude.yml`'s existing mechanism for mid-build feedback and change requests — were gated to `OWNER`/`MEMBER`/`COLLABORATOR` only, which the requester structurally never is (see "Support & handoff" below). So the requester's only real input was binary, on something already drafted; there was no "actually, make this red instead." Compounded by a separate bug found the same session: the comment's own *text* was never read into the prompt at all — `claude.yml` only ever fetched the issue's original title/body, using the comment purely as a re-trigger signal. Two consecutive `@claude` retries with materially different follow-up instructions produced near-identical responses, because both runs only ever saw the unchanged original issue text.

Fixed in two parts, same session: (1) the triggering comment's body is now fetched (via `gh api` on the comment id, never interpolating the untrusted text itself into bash) and spliced into the prompt as a "## Triggering comment" section that explicitly says newer instructions there override the original description; (2) `claude.yml`'s authorization moved from the job-level `if:` (collaborator-only, since it runs before checkout and can't read `README.md`) into a post-checkout `Authorize` step, mirroring `review-decision.yml`'s pattern — a collaborator's comment is authorized immediately, and anyone else's is checked against the recorded requester's login parsed from `README.md`, tolerating the same zero-match edge case `review-decision.yml` already had to fix (`|| true` on the extraction, or `pipefail` kills the step before the check ever runs). Every downstream step (resolving the issue, running Claude, journaling) is now gated on that authorization output.

**A bug in the first part of the fix, found immediately on the next real retry:** the explanatory comment added alongside the `gh api` fetch wrote out the literal expression syntax it was warning against, as prose (`` embedding `${{ github.event.comment.body }}` straight into this script ``) — not realizing GitHub Actions substitutes `${{ }}` across the *entire* raw text of a `run:` block before bash ever sees it, including inside `#` comments. The real triggering comment's text got spliced into that comment line at runtime, and everything after its first line ran as shell commands — `line 39: Explicit,: command not found`, the second paragraph of the actual retry instruction, executed as a command. Fixed by rephrasing the comment to describe the pattern without ever writing `${{ }}` literally. Lesson: never write GitHub Actions expression syntax inside a `run:` block's comments, even purely as documentation of what to avoid.

## Multiple concurrent projects & switching devices mid-build

A requester needs to be able to run more than one project at once and pick up where they left off on a different device — PC to check something at their desk, mobile to approve/reject on the go.

**Concurrency needs no design change.** Each project is already a fully independent repo with its own workflows and its own scoped `GH_PAT` (see `GH_PAT: token strategy`) — nothing in the pipeline assumes only one build is in flight, so running several at once already works today.

**Cross-device access is mostly solved by the same localStorage-PAT removal decided above, for the same reason.** Once neither intake nor approve/reject depends on a browser-local secret, there's no site-local session to lose when switching devices — GitHub's own account and notification system becomes the actual identity/cross-device layer. A requester who submits an ask on a PC and later gets a GitHub notification on their phone (design-doc PR merged, or a pending approve/reject) can act on it directly from GitHub's own mobile UI without ever logging into `ai-app-factory` itself, because there's nothing to log into.

**Decision: add `requesterGithub` to the `projects.json` registry, sourced from the issue author's GitHub login.** Implemented 2026-08-18 in `scripts/factory-new.sh` (superseding an earlier, same-day `requesterEmail` version — see "Requester PII is deliberately minimized" above). Existing registry entries predate this field and are left as-is rather than backfilled — the dashboard should treat it as optional. This unblocks a "my projects" view on the dashboard, filtering `projects.json` client-side by GitHub handle, for a requester juggling more than one project — **not yet implemented.**

**Also not yet implemented: the post-submit confirmation should hand back a direct, bookmarkable link to that project's own dashboard page**, rather than leaving the requester to find it later in a growing list of everyone else's projects.

**Visibility: there is no privacy boundary between requesters, or between a requester and the general public.** The dashboard, the `projects.json` registry, and every generated repo (including its README's "Requested by" section) are all fully public and unauthenticated by construction — the same static-hosting fact that rules out hardcoding a PAT (see "Why the write-path credential can't be hardcoded..." above) also means there's no server-side concept of "this data belongs to this requester." Any "my projects" filter is a client-side convenience for finding your own projects faster, not an access boundary — the underlying registry and every project's ask, status, and requester GitHub handle are visible to anyone who looks, including other requesters, by design of the whole system being public and static. This is a materially smaller exposure than the earlier name/email/phone version — a GitHub handle is information the requester already made public by having an account — but it's still worth remembering this is a fully public list, not a private one.

## Support & handoff

Every generated repo is created under `mmorrow24work` (via `factory-new.sh`'s local `gh auth`, run by the repo owner — not by the requester's own GitHub identity, even though that identity is now always known) and stays owned there for the entire build. The requester never gets *ownership* of it directly — that only happens via fork or clone, described below — but as of 2026-08-18 they can direct changes to it mid-build via `@claude` comments (see "PR review & merge" above), not just approve/reject something already drafted.

Every generated project should be explicit, in its own README, about two things:

**Getting help/giving feedback while it's still under active build.** The support channel *is* the pipeline's own comment/label mechanism, not a separate system: open an issue or comment on one. Apply `claude-go` to have the unattended pipeline attempt a fix or new work; comment `@claude` to give feedback or redirect something already in progress — authorized for any repo collaborator *or* the project's own recorded requester (parsed from the README's own "Requested by" line), not collaborators alone. Mention the human owner (`@mmorrow24work`) for anything Claude can't resolve or shouldn't attempt unattended (design decisions, ambiguous requirements, anything `lane:manual`).

**Taking it further once it's done: fork vs. clone.** Two different options, not one, added explicitly 2026-08-18 after a real requester asked how to get feedback into a build besides waiting to fork it later — forking was never the *only* path, just the one originally documented. **Fork** keeps the project connected to GitHub — its issues, PRs, and optionally the same unattended pipeline. This is a real, structural handoff, not just a suggestion: GitHub forks do **not** inherit the parent repo's Actions secrets, so `claude-go` on the fork simply has no `CLAUDE_CODE_OAUTH_TOKEN`/`GH_PAT` to run with — the pipeline stops working on the fork automatically the moment it's created, with no separate revoke step needed on the original owner's side. If the new owner wants to keep using the unattended pipeline going forward, they set up their own secrets on their fork (same `claude setup-token` / `gh secret set` steps documented in this repo's own `README.md`) and it becomes entirely theirs from there. **Clone** is simpler and has no continued connection at all — a plain `git clone`, no GitHub-side fork relationship, no `claude-go`, no `@claude`, no link back to the original — the right choice for someone who just wants the code, not the automation.

## Unattended pipeline hardening (UNATTENDED-BRIEF.md, changes 1-9)

**Trigger: `ai-app-factory-cov-pubs`'s unattended build stalled after one issue and sat idle for four hours.** Diagnosed 2026-08-19 in `UNATTENDED-BRIEF.md` (repo root) as three compounding root causes, not one: nothing advanced the queue after a PR merged (a human had to label every issue by hand); nothing merged the PR even once its checks passed; and there was no real CI check to gate a merge on in the first place — `claude.yml` had never been granted any test/package-manager tooling, so the agent could only ever say "I couldn't verify this" and stop. All nine changes below are template-level, not a one-off fix to `cov-pubs` — every future scaffold inherits them; `cov-pubs` itself was **not** retrofitted and needs its templates re-applied by hand if it's to benefit.

**Changes 1-2 (real CI + agents verify before opening a PR), implemented 2026-08-19, commit `e2d1eeb`.** `templates/*/.github/workflows/test.yml` (new, per project type — detects and runs the right suite) ships from scaffold time onward, so a required check exists before any PR ever opens. `claude.yml`'s `--allowedTools` grant expanded to include `pip`/`python`/`pytest`/`npm`/`node` (custom-script; nautobot-app and netbox-plugin already had their own equivalents) and the prompt now mandates actually installing dependencies and running tests for real — if they fail, comment + label `pipeline:failed` + stop, rather than open an unverified PR.

**Changes 3, 5, 6 (auto-merge, one-at-a-time, stop-on-failure), implemented 2026-08-19/20.** `factory-new.sh` now enables `allow_auto_merge` on the repo and sets branch protection requiring the `test` check, both immediately after `gh repo create` — confirmed live against a real throwaway repo that GitHub's branch-protection API accepts a required-check context that has never actually run (the "must run once before it's selectable" constraint is a Settings-UI-picker convenience, not an API requirement). `claude.yml` gained an "Enable auto-merge on the opened PR" step (`gh pr merge --auto --squash --delete-branch`, retried with backoff on the 422 GitHub returns when a PR isn't yet merge-ready) and a "Flag a workflow-level failure" step so a crash/timeout/turn-cap on the `claude-code-action` step itself — not just Claude's own self-reported test failure — still gets `pipeline:failed` and a comment; without it, a workflow-level crash left no PR and no label, a silent stall with no signal at all. All three `claude.yml` templates and `advance.yml` (below) now share one `concurrency: group: pipeline-${{ github.repository }}` so a manual `claude-go` label applied mid-run queues instead of racing.

**Change 4, 7 (auto-advance + runaway guards), implemented 2026-08-20: `templates/*/.github/workflows/advance.yml` (new, identical across all three types).** Fires on `pull_request: closed` filtered to `merged == true`, and re-triggers `claude.yml` via `workflow_dispatch` — Route A in the brief's own terminology: `GITHUB_TOKEN` cannot start a run via labeling (GitHub's anti-self-trigger-loop protection), but *can* start one via `workflow_dispatch`, so no PAT is needed for this step, only for opening PRs (already handled by `claude.yml`'s own `GH_PAT` preference). Before advancing it checks, in order: a repo-wide `pipeline:stop` label (halts immediately); an open `pipeline:failed` issue (halts until a human clears it); the `BUDGET_CEILING_USD` repo variable against `docs/journal.md`'s summed `**Estimated Cost:**` figures (halts + opens a `pipeline:stop`-labeled issue if at/over); then finds the next open `claude-go` issue sorted by milestone-then-issue-number (jq, verified against realistic and no-milestone mock data); a >25-issues-per-milestone cap is a last defensive check before dispatching. If none remain and zero issues are open at all, posts a "Pipeline complete" issue.

**Change 8 (get `lane:manual` off the critical path), implemented 2026-08-20: `templates/*/.github/workflows/seed-milestones.yml` prompt rewritten.** Previously instructed selective labeling — only the first milestone's issues got `claude-go`, everything else left for a human to label by hand later, which is exactly the "nothing advances the queue" failure this hardening pass exists to fix, now that `advance.yml` handles sequencing itself. Now instructs labeling every concretely-automatable issue `claude-go` in every milestone up front, and classifies anything not cleanly automatable into exactly one of three buckets, with the hard rule that no `lane:manual` issue may block a later one: automatable-with-a-secret becomes a normal `claude-go` issue, not manual; genuinely-human-judgement stays `lane:manual` but moves to the highest-numbered milestone so it sits at the *end* of the sequence; one-time setup (custom domain, Pages) isn't an issue at all — it's front-loaded into provisioning (change 9, below).

**Change 9 (front-load human inputs into provisioning), implemented 2026-08-20.** `factory-new.sh` gained `--enable-pages` (commits `templates/_shared/pages-deploy.yml.tmpl` into the scaffold and turns on Pages with `build_type=workflow` via the GitHub API — using the human's own `gh auth`, before any `GH_PAT` is even minted, since `GH_PAT` deliberately excludes `Workflows` scope and cannot push workflow files itself), `--set CUSTOM_DOMAIN=...` (writes `CNAME` and sets the Pages custom domain via API; DNS itself is still the human's job — this only does the GitHub-side half), and `--set BUDGET_CEILING_USD=...` (`gh variable set`, read by `advance.yml`'s budget check above). `CLAUDE_CODE_OAUTH_TOKEN`/`GH_PAT` collection was already front-loaded — `factory-secrets.sh` runs immediately after `factory-new.sh`, before the design doc is even seeded — so change 9 didn't need a new mechanism for those, only documentation that the existing one already satisfies it.

**Known gaps, honestly not closed by this pass:** `ai-app-factory-cov-pubs` itself is not retrofitted — these changes only benefit projects scaffolded from this point forward. The brief's own suggested end-to-end proof (provision a fresh project and walk away from design-doc approval to a merged PR with no further input) has not been run live in this session — each change was verified in isolation (YAML validation, jq/bash logic against real and edge-case data, live API calls against a disposable throwaway repo, read-only queries against the real `cov-pubs` repo), not as one continuous live pipeline run. `netbox-plugin`'s `test.yml` working-directory assumption is unverified against a real NetBox instance. `--enable-pages` is opt-in, not automatic — a project needing Pages that omits the flag at provisioning time still ends up needing a human step, just one `seed-milestones.yml` is now instructed to flag explicitly rather than silently invent a blocking issue for.
